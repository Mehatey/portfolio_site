{% comment %} ══════════════════════════════════════════════════════════════════ THE WHOLE PAGE IS ONE PHOTOGRAPH The hero is graded: bloom, grain, chromatic aberration, a vignette, an ACES shoulder. Everything below it was raw CSS on a flat ground. So the page read as a striking hero bolted onto a document -- the seam was visible at exactly the point where the canvas ended, because one half was photographed and the other was rendered. This is the grade, applied to the whole document. Two layers, fixed to the viewport, above everything and inert to the pointer: GRAIN real noise, generated once into a 128px tile and stepped through four positions a second. Film grain does not slide -- it is a new field of silver every frame -- so the movement is a steps() animation rather than a smooth translate, which is the difference between grain and a moving texture. VIGNETTE a corner falloff. Every lens has one, and its absence is a large part of why a CSS page reads as flat: real images are darker at the edges and the eye reads that as depth. WHY NOT A SHADER OVER THE PAGE Because a browser gives no way to read back rendered DOM pixels, so a full-screen post pass cannot sample what is underneath it. Everything here is therefore ADDITIVE or multiplicative and needs no read: grain is overlaid, the vignette multiplies. The two effects that would need the backbuffer -- aberration and bloom over DOM content -- stay inside the hero's own canvas, where the pixels are ours. The tile is generated in JS rather than shipped as a PNG. 128x128 of real random bytes is about 16KB of ImageData and costs one frame at boot; the same thing as a file is a network request for something the CPU can make faster than it can download. {% endcomment %}
